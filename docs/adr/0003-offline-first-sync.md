# ADR 0003：离线优先 + 幂等同步 + 最后写入胜

- **状态**：Accepted
- **日期**：2026-10-21
- **决策者**：前端与后端团队

## 背景

用户可能在网络不稳定或完全离线时继续编辑。早期同步在每次保存时直接请求后端，断网重试会重复创建项目 / 元素，且多端同时编辑时无法判断谁的数据更新。

## 决策

1. 所有编辑先写 IndexedDB，并进入 `syncQueue`。
2. 客户端为每次同步生成 `Idempotency-Key`，后端通过 `IdempotencyKey` 表按 key 去重。
3. 队列按项目合并为最新快照，恢复网络后重放。
4. 冲突采用最后写入胜；服务端在响应中返回 `conflict`，前端提示用户云端修改已被覆盖。
5. 离线创建的项目在首次同步后使用服务端 id 回填并迁移本地引用。

## 理由

- 本地写入不受网络影响，交互始终即时。
- 幂等键把“至少一次”重试变成可安全重放的写入，解决重复创建。
- 快照合并避免离线期间的大量中间状态逐个上传。
- 最后写入胜实现简单、可预测，适合当前单用户多设备场景；CRDT 的复杂度暂不值得。

## 后果

- 冲突会丢失一端的修改，因此必须给出明确提示，不能静默覆盖。
- 服务端需要维护幂等表并设置清理策略，否则会持续增长。
- 队列合并意味着无法回放离线期间的每一个中间步骤，仅保留最终状态。
- 真正的多人实时协作仍需 CRDT / OT，本决策不覆盖该场景。
