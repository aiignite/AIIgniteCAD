# ADR 0020：AI 差异化的三个落点（计划预检、跨图纸快照与一致性、变更说明）

- 状态：已采纳
- 日期：2026-10-26
- 相关：ADR 0005（预览与单步撤销）、ADR 0014（计划模式与检查面板）、ADR 0015（设计约定与多方案）、ADR 0017（约定下沉到确定性检查）、ADR 0018（工具契约与拒绝回环）

## 背景

P0–P3 已经把 AI 做成「能画、能改、能检查」：工具循环、计划模式、多方案、质量门禁、约定注入都已落地，
但三处仍有明显落差，且都不在「再加一个工具」这一层：

1. **约定只在事后生效**。约定已经驱动检查面板、质量门禁与 `check_drawing`，
   但用户在计划卡上点「执行计划」时看不到这份计划会违反哪条约定——问题总是在预览里才暴露，
   而此时用户已经确认过一轮。
2. **图纸之间是孤岛**。项目里有多张图纸，但 AI 的上下文、检查面板、工具都只认当前这一张；
   项目级的矛盾（一处按 mm 画、一处按 m 画，字高 3.5 与 5 混用，图层清单各写一套）无法被发现，
   也没有把一张图复用到另一张图的路径。
3. **预览只说数量**。预览弹窗给出「+3 −1 ~2」，但用户要判断的是「具体动了哪里、动到了哪个图层」；
   模型自述的变更说明不可信，几何差分才是事实。

## 决策

### 1. 约定必须在计划阶段生效：计划预检

新增 `lib/planReview.ts`：计划确认前按**当前选择集**把写步骤逐步在草稿上模拟执行，
再用与预览门禁**同一套** `reviewPreview` 对比改动前后，得出「这份计划会引入哪些问题」。

- 只模拟、不落图：预检不写画布、不占撤销步，用户取消计划不会留下任何痕迹。
- **按步骤归因**：用每步的 `changedIds` 与新增问题求交集，把问题算在具体步骤上；
  同一个问题只算在最先引入它的步骤。全局性问题（约定图层为空、缺标注）没有具体图元，不强行归因。
- 只读 / 视图 / 无工具步骤不算失败——「先检查再修改」是正常计划，误报会让用户不再信预检。
- 复用的代价是行为一致：预检与门禁只要有一处口径不同，用户就会看到「预检通过但预览报错」。

### 2. 跨图纸用「快照插入」，不做持续引用

`lib/crossDrawing.ts` 把另一张图纸的图元**一次性**复制进当前图纸：

- 基点取源图包围盒左下角。用原点当基点时，远离原点的图纸插入后会跳到画布外，
  用户看到的现象是「插入后什么都没出现」。
- 图元重新编号为 `xref:<sourceId>:<n>` 并共享 `groupId`，可整体移动 / 删除；来源可追溯。
- 块引用（`BLOCK_REFERENCE`）跳过并计数：它依赖来源图纸的块定义，目标图纸不一定有。
- 单次上限 2000 图元，超出截断并在通知里说明。

**取舍**：这不是 xref。代价是来源图纸更新不会回灌；收益是不需要外部引用的加载失败处理、
循环引用检测与版本漂移对账，也符合块插入已经确立的「符号展开复制」语义。
真要做持续引用时，这一层可以整体替换，不影响上层 UI。

`services/drawingLoader.ts` 读取源图纸时**不调用 `openProject`**：
浏览别人的图纸不应改写服务端「最近打开」。服务端不可用时回退本地 IndexedDB 文档。

### 3. 一致性检查只吃清单事实

`lib/projectConsistency.ts` 的输入是「名称 + 图元数 + 设计约定」，不读图元正文：

- 能在图纸列表上直接跑，打开检查面板不会触发 N 次全图请求。
- 规则收敛为 8 条：重名、空图纸、约定缺失、单位 / 字高 / 精度 / 制图标准不一致、约定图层清单不一致。
- **只比较显式设置过的字段**：没设置不等于不一致，否则「只有一张图设了字高」会被报成矛盾。
- 「约定图层不一致」只报**只在部分图纸登记**的层，不报整体集合不同——
  后者会让用户拿到一句「图层不一致」，却不知道该补哪个层。

### 4. 变更说明用几何差分，不做操作归因

`lib/changeExplanation.ts` 从 `diffElementSets` 展开逐条明细，
按「新增 → 修改 → 删除」排序，给出图元类型、图层与几何摘要，并按图层聚合增删改。

- **为什么不按操作归因**：一次 `MOVE` 可能改动 20 个图元、一次 `DELETE` 与后续 `ADD` 可能互相抵消，
  把「哪条变更属于哪个工具调用」只能是猜测。预检可以归因（它逐步模拟、有中间草稿），
  预览不能——预览只有前后两份图元。诚实做法是把「模型说做了什么」（操作清单）与
  「实际发生了什么」（几何差分）并排给出，由用户对照。
- 文本可复制：评审、留档、回填给模型都走同一份 `text`，避免 UI 与导出两套说法。

### 5. 判定「同一条问题」要把描述算进去

`reviewIssueKey` 从 `code + ids` 改为 `code + ids + message`。
把图元从图层 0 移到另一个未登记图层时，规则与图元都没变，但问题内容已经变了；
旧口径会把它当成旧问题漏报——这在计划预检里表现为「预检说没问题，预览却报错」。

## 后果

- 计划卡多了一次模拟执行：≤12 步、每步只算一次差分，最终一次 `reviewDrawing`；
  放在宏任务里执行，不阻塞卡片首帧。大图上预检有成本，但只在待确认的计划卡上发生一次。
- 预检结果依赖当前选择集：计划里的步骤若省略 `ids`，预检按当前选择集解析；
  用户换选择集后预检会重算（卡片以步骤签名 + 图元数 + 选择数作为 key）。
- 快照插入把图元变成普通图元：来源图纸改名 / 删除都不影响已插入的内容，
  用户需要「同步更新」时必须重新插入（会再产生一份，需要自行删除旧的）。
- 一致性检查在图纸列表基础上做，列表里的 `elementCount` 可能有延迟（本地新建未同步），
  因此「空图纸」是提示级而不是错误级。
- `reviewIssueKey` 加入描述后，检查面板里已忽略的问题在描述变化后会重新出现——这是期望行为。
